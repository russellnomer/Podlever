### Phase 1A — PodLever Core Orchestration Engine

**1. Executive Summary**
Phase 1A establishes the architectural skeleton of PodLever as a Next.js 15 App Router application: typed configuration, Replit PostgreSQL + Drizzle schema, an AuthProvider abstraction gated by an Environment Discovery task and a mandatory Human Checkpoint, Owner-only role protection, a Repository + Service layer for Episode and Asset only, a strongly-typed Episode Finite State Machine with optimistic locking (`fsm_version`), an append-only PipelineEvent log with idempotency guarantees, a verification script, and three ADRs. No product features (AI, media, uploads, jobs, publishing, analytics, multi-tenancy, billing) are built. Success means a subsequent coding agent can execute every task without making new architectural decisions, and `scripts/verify-fsm.ts` proves the FSM, locking, and idempotency behavior end-to-end.

**2. Architecture Overview**

* **Framework:** Next.js 15 App Router, TypeScript strict, Tailwind, Zod. shadcn/ui initialized non-interactively.
* **Layering (mandatory):** Server Action / Route Handler / Job → Service → Repository → Drizzle. Server Actions, Route Handlers, and Jobs never call Repositories directly. `/jobs` exists as an empty placeholder.
* **Persistence:** Replit PostgreSQL via Drizzle ORM; minimum normalized schema (User, Episode, Asset, PipelineEvent).
* **Identity:** A narrow AuthProvider interface in `/providers`; concrete implementation chosen only after Environment Discovery + Human Checkpoint. Middleware reads identity only — never touches the database.

**3. Phase 1A Task Breakdown**

* **T1 — Project Initialization:** Next.js 15 App Router + TypeScript + Tailwind + Zod scaffold.
* **T2 — Environment Discovery (Identity):** Empirically determine active Replit identity mechanism.
* **T3 — HUMAN CHECKPOINT (Mandatory Halt):** Agent halts, reports T2 findings, waits for human confirmation before AuthProvider design.
* **T4 — Typed Configuration:** `/config` module validating all env vars at startup with Zod.
* **T5 — Database Schema + Migrations:** Drizzle schema in `/db` (users, episodes, assets, pipeline_events). Plan `drizzle.config.ts`.
* **T6 — AuthProvider + Middleware + Safe User Sync:** Implement narrow interface. Middleware reads identity only. User upsert/sync implemented as non-render pathway.
* **T7 — Owner-only Role Protection:** Role check enforced in Service layer entry points.
* **T8 — Repository + Service Layer:** `EpisodeRepository` and `AssetRepository` exposing domain-oriented methods. Native Drizzle transactions used.
* **T9 — Episode Finite State Machine:** Strongly-typed FSM in `/server`. Optimistic-lock UPDATE guarded by `fsm_version`. INSERT PipelineEvent with caller-supplied idempotency key.
* **T10 — Minimal Verification UI:** Minimum UI needed to verify auth + owner protection interactively.
* **T11 — Verification Script:** `scripts/verify-fsm.ts` executed via `tsx` covering all four required FSM behaviors.
* **T12 — Architectural Decision Records:** Three ADRs in `/docs/adr` (Architecture, Repository Pattern, FSM).

**4. Verification Strategy & Exit Criteria**
Complete when: all verification steps pass (Static, Build, Schema, FSM script, Auth manual check); T3 checkpoint decision recorded; three ADRs written; no layering violations found by code search. Do NOT proceed to 1B if idempotency is enforced anywhere other than the DB constraint or `verify-fsm` is flaky.
